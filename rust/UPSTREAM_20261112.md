**Fact** denotes an observation from those artifacts or runs. **Inference** denotes interpretation or a porting recommendation. Exact means decoded PNG samples at 8 bpc, raw AE words at 16 bpc, and float bit patterns at 32 bpc; no tolerance is used. These are AEXCompat CPU results, not native AE saved-project acceptance, Mac qualification, GPU tests, or exhaustive behavior proofs.

## Interpretation of the update measurements

**ColorKeep — facts and static interpretation.** The generic old/new campaign is exact in 36/36 general and 912/912 sensitivity route-cases. It does not exercise every important key match: most random palette colors do not match source pixels, and most one-control palette probes remain inactive at the default enabled count. The hub's [seven unknown-function decompilations](tools/triage/runs/U-triage-20261112/ColorKeep-unknown-decompile.json) show new depth callbacks at RVAs `0x15c0` (202 bytes, 8 bpc), `0x1690` (220 bytes, 16 bpc), and `0x1780` (189 bytes, float). Their normalized RGB comparisons use a 0.0001 threshold and do not test alpha. The [conversion helpers](tools/triage/runs/U-triage-20261112/ColorKeep-pixel-conversion-decompile.json) normalize 8/16-bit channels and pass float channels through. In contrast, the qualified old Rust `color_keep::pixel` compares all four ARGB channels, with integer quantization at 8/16 bpc. This is a static reason to test translucent exact-color matches, not a reason to call the random corpus globally equivalent.

Funcdb finds no qualified Rust candidate for a new ColorKeep function. The old unmatched callbacks at RVAs `0x1280` (761 bytes), `0x1580` (720 bytes), and `0x1850` (574 bytes) do have qualified mappings to the PF16/PF8/PF32 arms of `rust/plugins/color-keep/src/lib.rs::pixel`. Thus the implementation target is known even though automated cross-version matching does not establish the new mapping. Only seven new functions, totaling 2,039 bytes, are unknown to the full ten-original database; the large triage unmatched set also contains shared SDK/runtime code.

**DistanceGradation — facts.** General cases have 27 mismatches and nine exact results; sensitivity has 72 mismatches and six exact results, with no failed renders in either campaign. Untouched defaults differ at all depths. The 31x19 default witness changes 353 pixels; at 8 bpc only alpha differs, while RGB is identical. For example, the retained first row has alpha 15/37/126 in the old build versus 31/126/253 in the new build. Padding is untouched/off in this comparison. The sensitivity baseline already differs, so mismatches under many separate controls do not prove independent changes in every control's implementation.

**DistanceGradation — static facts/inference.** Both `IPPCODE` and `IPPDATA` are byte-identical between the old and new 2025 binaries ([section hashes](tools/triage/runs/U-triage-20261112/DistanceGradation-old-new-sections.json)); there are no new PE imports. The three 3,753-byte unmatched render drivers are at RVAs `0x1171050`, `0x1171f20`, and `0x1172df0`. The [focused decompilation](tools/triage/runs/U-triage-20261112/DistanceGradation-focused-decompile.json) shows slot-13 checkout followed by padding-dependent dimensions and offsets. These observations support concentrating review on the changed effect/host code rather than re-porting the entire linked IPP image. They do not establish the cause of the default alpha change or the full native AE extent contract.

**Smoother2 — facts.** General cases have 27 mismatches and nine exact results; sensitivity has 90 mismatches and three exact results, with no failed renders. The behavioral default witness changes 31 pixels confined to the rightmost two columns at 31x19. Its default differs at all three depths. The independent sensitivity default also differs; only the Smoothness-zero probe is exact in that sweep. Smooth Range is omitted by triage because its parameter kind changed, so the separate old-domain oracle campaign is needed for that control.

The completed [old-domain Smoother2 run](tools/triage/runs/U-triage-20261112/old-domain-Smoother2/summary.json), which includes explicit old numeric Smooth Range values, has four exact and eight mismatched cases per depth, with no render failures. The current Rust-domain campaign has the same counts. This establishes that valid old numeric requests are accepted in these headless renders; it does not establish AE's saved-slider/keyframe migration.

Two additional per-process replays of each default witness for both Smoother2 and DistanceGradation reproduce each side's output byte-for-byte: 12 replayed pairs, 24 matching side hashes ([stability evidence](tools/triage/runs/U-triage-20261112/default-replay-stability.json)). The observed default differences are repeatable on this host.

**Smoother2 — static facts/inference.** New imports are `cbrtf`, `abort`, `_vcomp_set_num_threads` and `omp_get_max_threads`. The new 396-byte function at RVA `0x5520` performs three cube-root calls and color-matrix arithmetic ([decompilation](tools/triage/runs/U-triage-20261112/Smoother2-cbrtf-decompile.json)), consistent with the documented Oklab path. Exact cube-root behavior needs qualification under the port's numerics contract. Seventeen triage **referenced-data-only** change candidates map through funcdb to qualified Rust geometry routines; funcdb fingerprints those bodies as exact. That normalizer disagreement is a review caveat, not proof that 17 geometry algorithms changed. The detailed old/new RVAs, sizes and Rust symbols are retained in the mapping review list.

**ColorKey — fact.** All primary behavioral and sensitivity attempts are incomplete on the new-build side because of the harness parameter limit. No pixel-equivalence or pixel-regression conclusion can be drawn from those failures. The 25 existing Use Color default changes and expanded declarations are independently confirmed by both public inventory and supplementary capture.

## Kit limitations and follow-up requirements

- **ColorKey render blocker:** the new binary exposes 1,623 controls, while the harness encoder rejects slots above `MAX_PARAMETERS = 1024`, including on an empty-assignment render because it encodes discovered defaults. The observed error is `interactive parameter is out of range`. The same encoder also caps payloads at 16,384 bytes. The retained [source excerpt and hashes](tools/triage/runs/U-triage-20261112/harness-parameter-limit.json) identify both constraints. Update the broker/worker transport limits consistently, or add supported sparse-default transport, before qualifying this release's ColorKey behavior. No harness source was changed.
- Triage has no `--resident` option and performs each paired sensitivity render in fresh processes. Its full one-control sweep can be expensive for large palettes. Oracle resident mode is used for the separate campaigns, with per-process replays retained for every mismatch/failure.
- Triage matches controls by slot/name/kind. Smoother2's retyped Smooth Range is unmatched and therefore omitted from its old/new generic campaign; an explicit same-slot old-domain campaign is required to examine old numeric values.
- Generating requests from new inventories also asks old Rust ports to accept appended controls and wider ranges. Those failures measure an interface gap, not pixel-kernel error. Separate Rust-domain runs are required to measure existing supported controls.
- A resident batch containing invalid assignments can reject valid sibling cases too. Oracle's generic `batch report route/isolation differs` diagnostic can obscure the underlying validation error in the saved batch stdout. Preserve batch and per-process results separately; replay successes do not convert the failed baseline into passes.
- Resident authority replays are serial after all resident workers exit. Expensive padding/blur extrema can therefore consume the full frame bound repeatedly. A future tool change should run those replays within the same global `--jobs` ceiling and support explicit cost-bounded follow-up plans, while retaining every failed baseline. Timeouts do not prove a plug-in cannot render in AE.
- The generic palette corpus can produce trivial no-match output and leave later palette controls inactive. Add source-color-matched, translucent, and explicitly activated palette witnesses; the ColorKeep investigation shows why those are necessary.
- AntiAntiAlias's button at slot 3 is captured but rejected by the scaffold validator (`unhandled or inconsistent parameter type at slot 3`). Button declarations and user-change action support are needed before scaffold generation can cover this plug-in. A zero custom-event mask does not establish absence of dynamic UI.
- AntiAntiAlias's default, random, automatic-palette and explicit-manual-palette Smart renders all fail on this harness at every declared depth. The repeated diagnostic is session close rejection `invariant=worker_not_ok`, with 17 acquired/released suite leases and no live leases/references in the default witness. The failure stdout exposes only classification, failure stage and parameter metadata, so it does not identify a numerical or suite root cause. Preserve the pre-close worker failure/parameter lifecycle trace in a future harness change. The [Smart-render decompilation](tools/triage/runs/U-triage-20261112/AntiAntiAlias-smart-render-decompile.json) and [parameter helper](tools/triage/runs/U-triage-20261112/AntiAntiAlias-prerender-helper-decompile.json) are bounded investigation leads, not proof of the cause. Failed cold times are time-to-failure, not render benchmarks. Neither native-AE failure nor 2025/2026 pixel equivalence follows from these results.
- Saved projects, animated parameter migration, conditional UI, button actions, HDR sources, temporal behavior, GPU execution, native AE and macOS remain outside this task's headless measurements.
- Ghidra changed/added/removed counts are matching results, not semantic edit counts. Compiler changes can move implementation into unmatched functions. Function bytes sum discovered body sizes; they are not PE sizes or deduplicated coverage.
- Funcdb `verified_rust` mappings refer to existing plugin-corpus qualification of the old implementation. Exact/fuzzy reuse candidates in a new binary do not certify that new function. Sparse mappings, especially inside statically linked libraries, must not be treated as complete Rust coverage.
- **Shared-workspace source drift:** oracle and scaffold sources changed externally during this job; this job edited neither. Starting/current hashes, timestamps and current snapshots are retained in [tool-source-drift.json](tools/triage/runs/U-triage-20261112/tool-source-drift.json). Oracle case manifests retain on-disk tool identities, but a file hash taken after an external edit does not prove the already-imported Python module was reloaded. Treat the job as multiple bounded campaigns, not qualification of one immutable kit revision. Follow-up witnesses run in a fresh process after the observed change.
