# OLMDirectionalBlur Natural Continuation Review 20260718

## Verdict

The two claims you asked about hold up under focused inspection:

- The claimed downstream write is a real AEX memory-write event, not a fabricated ledger value.
- The claimed output callback is a real execution of `0x180006b30`, with the usual bounded-host caveat that the PF_Iterate8 host side is shimmed while the callback body itself is actual AEX code.

I did not find evidence that `fixture_status=blocked` itself creates the final `pass`. In the kernel report, that blocked state is explicitly the pre-continuation fixture phase, and the same report records a later live continuation from `0x180002068` to the global return sentinel.

## Validation Notes

### 1. Downstream write

- The continuation kernel traces live overlapping writes to the chosen writer cell with a Unicorn `UC_HOOK_MEM_WRITE` hook in [tools/emulation/test_olmdirectionalblur_iterate8_natural_prerender_followup_20260717.py](../../tools/emulation/test_olmdirectionalblur_iterate8_natural_prerender_followup_20260717.py) lines 117-125.
- The captured report records the first overlapping write at `0x2002df4c` with `rip=0x180002196` in `target.first_distinct_write_0x8078_to_0x8090`.
- `objdump -d --start-address=0x180002170 --stop-address=0x1800021b0 plugins_2025/OLMDirectionalBlur.aex` shows `0x180002196` is an in-binary instruction: `movss %xmm3, 0x4(%r9)`.

Conclusion: this is a genuine actual-AEX internal float-buffer write. It is not the final PF output store, but the continuation artifact does not claim that it is.

### 2. Output callback

- The kernel's `call_actual_callback(...)` helper executes the real callback body on a private stack, requires return to `PRIVATE_RETURN`, and checks that the outer Iterate8 frame is preserved: [tools/emulation/test_olmdirectionalblur_iterate8_natural_prerender_followup_20260717.py](../../tools/emulation/test_olmdirectionalblur_iterate8_natural_prerender_followup_20260717.py) lines 149-190.
- The `real_output_callback_0x180006b30` checkpoint is recorded only after `actual_output(...)` calls `call_actual_callback(loader, OUTPUT, ...)`: same file, lines 228-236.
- The host fixture still routes PF_Iterate8 through `model_output(...)`: [tools/emulation/dblur_fullrender_host_fixture_20260711.py](../../tools/emulation/dblur_fullrender_host_fixture_20260711.py) lines 922-929.
- The separate caller-contract witness records the real `0x180006b30` ABI at entry and that the callback returned zero: `refs/conformance/olmdirectionalblur_caller_contract_20260717.json`.

Conclusion: the callback body is genuinely actual AEX, but the claim remains bounded and should not be read as "full actual AE host output path."

### 3. `fixture_status=blocked`

- The kernel report sets `natural_prerender_owner.fixture_status` to `blocked`, but also tags that state as `fixture_report_phase = "before explicit live-state continuation"`.
- The same report records `outer_continuations[0] = {start_rip: 0x180002068, end_rip: 0x90000000}` and final `status = pass`.
- The runner preserves the initial blocked reason only as historical context in [tools/emulation/run_olmdirectionalblur_natural_continuation_20260718.py](../../tools/emulation/run_olmdirectionalblur_natural_continuation_20260718.py) lines 114-119.

Conclusion: this blocked fixture status is not, by itself, a false pass. It is a staged observation from before the explicit continuation step.

## Finding

### Medium: pass classification is detached from the current kernel execution

The runner has a separate false-pass hazard:

- [tools/emulation/run_olmdirectionalblur_natural_continuation_20260718.py](../../tools/emulation/run_olmdirectionalblur_natural_continuation_20260718.py) lines 93-96 always load the fixed kernel report path if it exists.
- Lines 187-190 derive `status = "pass"` entirely from checkpoint content, without requiring `returncode == 0` or `kernel_report["status"] == "pass"`.
- [tools/emulation/test_olmdirectionalblur_natural_continuation_20260718.py](../../tools/emulation/test_olmdirectionalblur_natural_continuation_20260718.py) lines 25-26 explicitly accept either `pass` or `blocked`, so the smoke test does not guard against that classification gap.

This means the reviewed `fixture_status=blocked` field is not the dangerous part. The real risk is that stale or mismatched kernel evidence could be re-labeled as a fresh `pass`.

Resolution: fixed after review. The runner now removes the fixed report before
launch, accepts only a report generated by a successful current subprocess,
restores prior evidence on failure, and requires both `returncode=0` and kernel
`status=pass`. The regression test covers a stale pass report plus a failing
kernel command.
